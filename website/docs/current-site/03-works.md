## 目的

AccelHackが対応してきた実績を、支援内容から探せる形で紹介します。上部のカタログで事例を絞り込み、その下に全事例の概要を縦に並べます。各事例をクリックすると、より詳しい説明をモーダルで表示します。

## ページ名称

- 下層ページ見出し: `Works`
- URL: `/service`
- トップ・右側タブの表示名: `Service`

## カタログ

Eyebrow:

> ACCELHACK / WORKS

Message:

> 領域を横断して、<br>
> 実績を見つける。

Description:

> 業界や支援範囲から、AccelHackが向き合ってきたプロジェクトを探せます。

- Category: すべて / プロダクト / 業務・事業 / 社内事例
- Support: 課題発見 / 設計 / 開発

カタログのカードとインデックスを押すと、ページ下部の該当事例まで移動します。絞り込みは上部カタログだけに適用し、下部には常に全5件を表示します。

## CASE 01

Client:

> 株式会社IEGAO 様

Headline:

> 他社1年・1200万円の見積もりを大幅圧縮

Category / Support:

> 業務・事業 / 課題発見 / 設計 / 開発

Summary:

> 大規模な開発計画をそのまま進めるのではなく、事業に必要な機能と優先順位を整理。最初に解くべき課題へ範囲を絞り込み、短いサイクルで検証と改善を重ねられるプロジェクトへ再設計しました。

Inside the Project:

当初の計画では、完成まで約1年、費用は1200万円規模の見積もりが提示されていました。しかし、すべての機能を一度につくる進め方では、完成時に事業環境や現場のニーズが変わっている可能性があります。

そこで、関係者へのヒアリングを通じて業務の流れと本当に必要な機能を整理。プロジェクトを複数の段階に分け、効果を確認しながら次の開発内容を決められる構成へ見直しました。

初期投資と開発期間を抑えるだけでなく、利用者の反応を早い段階で得られるため、事業に必要な機能へ継続的に集中できる開発体制を目指しました。

> 要確認: 期間・金額・比較対象・実際の成果。

## CASE 02

Client:

> 渡辺工業株式会社 様

Headline:

> 自社ノウハウを“売れる商品に”

Category / Support:

> プロダクト / 課題発見 / 設計 / 開発

Summary:

> 社内で培われてきた専門的な判断や業務ノウハウを整理し、担当者の経験だけに依存しない仕組みへ転換。社内業務の効率化に留めず、顧客へ提供できるプロダクトとして成立する形を設計しました。

Inside the Project:

現場には長年の経験によって蓄積された価値あるノウハウがある一方、その多くは担当者の頭の中や個別の資料に分散していました。まずは、業務のどの場面で、どの情報を使い、どのような判断をしているのかを可視化しました。

整理した判断基準をプロダクトの機能へ置き換え、誰が使っても一定の品質を保てる操作とデータ構造を設計。社内で実際に利用しながら改善できる状態をつくり、将来的に社外へ提供する際にも拡張しやすい構成を目指しました。

業務改善のためのシステムをつくるだけでなく、自社の強みを新しい商品として届けるところまでを見据えたプロジェクトです。

> 要確認: 商品名、提供範囲、公開可能な成果。

## CASE 03

Client:

> 某家電メーカー 様

Headline:

> Microsoftだけで完結するAX/DX

Category / Support:

> 業務・事業 / 設計 / 開発

Summary:

> 既に社内で利用されているMicrosoft環境を活かし、情報収集、申請、確認、集計までの業務を一つの流れに統合。新しいツールを増やさず、現場が使い慣れた環境の中でAX/DXを実現しました。

Inside the Project:

業務ごとに異なるファイルや連絡手段が使われていたため、情報の転記、進捗確認、集計に多くの手作業が発生していました。また、新しい業務システムを導入すると、アカウント管理や操作教育などの負担が増える懸念もありました。

そこで、既存のMicrosoft環境を中心に業務フローを再構成。入力された情報が関係者へ連携され、承認や更新の状況を追跡できる仕組みを設計しました。

現場に新しい操作を強いるのではなく、使い慣れた環境を業務の基盤として育てることで、導入時の負担を抑えながら継続的に改善できる状態を目指しました。

> 要確認: AXの定義、利用サービス名、対象業務、公開可能な効果。

## CASE 04

Client:

> 某専門商社 様

Headline:

> 面倒な請求書照合業務をAIで1/10の省力化

Category / Support:

> 業務・事業 / 課題発見 / 設計 / 開発

Summary:

> 形式の異なる請求書から必要な情報をAIで読み取り、社内データとの照合結果を自動で整理。担当者がすべてを目視確認する運用から、確認が必要な箇所だけを判断する運用へ変更しました。

Inside the Project:

取引先ごとにレイアウトや記載方法が異なる請求書を、担当者が一件ずつ確認し、社内の発注・取引データと照合していました。件数が増えるほど作業時間が膨らみ、入力ミスや確認漏れを防ぐための再確認も必要でした。

請求書から取引先、金額、日付などの情報を抽出し、対応する社内データと照合する流れを設計。判断に迷うものや差異があるものだけを担当者へ提示し、人が確認すべき対象を絞り込みました。

単純作業をAIへ移すことで、担当者は例外への対応や最終判断に集中できます。従来と比較して、照合作業にかかる手間を約10分の1へ抑えることを目指しました。

> 要確認: 「1/10」の算定条件、対象件数、実績値か目標値か。

## CASE 05

Client:

> 社内事例

Headline:

> 領収書の振り分けをAIに丸投げ

Category / Support:

> 社内事例 / 課題発見 / 設計 / 開発

Summary:

> 領収書の内容をAIが読み取り、用途や勘定科目の候補ごとに自動で分類。人が一枚ずつ確認して振り分ける作業を減らし、例外だけを確認できる社内フローを構築しました。

Inside the Project:

領収書の整理では、記載内容を読み取り、利用目的を確認し、適切な分類先を選ぶ作業が繰り返し発生します。件数は一件ずつであれば小さくても、月末に集中すると担当者の大きな負担になります。

画像から必要な情報を読み取り、日付、金額、支払先、内容をもとに分類候補を提示する仕組みを社内で試作。確信度が低いものや通常と異なるものだけを人が確認する流れにしました。

まず自社業務で利用することで、AIに任せられる判断と人が確認すべき判断の境界を検証しています。小さな業務からAI活用を始め、実務の中で改善を重ねる社内事例です。

> 要確認: 使用モデル、分類項目、削減時間、現在の運用状況。
